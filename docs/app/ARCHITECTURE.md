# Code architecture

English · [Italiano](ARCHITECTURE.it.md)

How Atollo's code is organized and where a new change goes. The reasons behind the choices are in [DECISIONS.md](DECISIONS.md) (in Italian), usage in the [Guide](https://nabre.github.io/atollo/guide/), what is new in [CHANGELOG.md](CHANGELOG.md) (in Italian), tests in [TESTING.md](TESTING.md). Open work is in the [GitHub issues](https://github.com/nabre/atollo/issues).

## Requirements

From the initial prompt (October 13-14, 2026), valid for every change; each one has a test or an item in the TESTING.md checklist.

1. **No installation**: a single executable (on macOS the `.app` bundle, on Linux the AppImage), no installer, service or scheduled task.
2. **No administrator rights** (`asInvoker` manifest on Windows). What only an administrator can do for Docker Sandboxes (turning on the hypervisor, an AppArmor profile on Ubuntu) Atollo never does: the "No VM" notice shows the command to copy (D-167).
3. **No writes outside the kit**: no registry, system `PATH`, real `%APPDATA%`, `%LOCALAPPDATA%` or `%TEMP%`; the only exceptions are the ones declared in the README (D-41, D-70, D-90, D-115) and, for Docker Sandboxes, the ones D-175 lists (the Docker sign-in of `sbx login`, the per-sandbox secret commands in the system's credential store, the daemon's `sboxd-<id>` junction and `gvisor` folder in the system temp, the AppArmor profile on Ubuntu). Sandboxes, disks, images, settings and logs of `sbx` stay in `data`.
4. **Paths relative to the kit root**, which works from any folder (spaces, parentheses, `&`) and after a move (relocation at startup).
5. **WebView in the kit**: the system WebView2 or a fixed one in `data\apps\…\webview2\`, never the bootstrapper; WebView data in `data\webview2\` (on macOS it stays in `~/Library/WebKit`, a declared trace).
6. **Always the kit's environment**: every process started gets the environment from `env\`, never the user's `PATH` unfiltered.
7. **A single instance per kit**, with a notice about the other open copies.
8. **No orphan processes**, even if the app is force-closed (Job Object on Windows, groups and a guard on macOS and Linux: D-07, D-105).
9. **Security**: Tauri commands only for the `main` window, editor windows without IPC, strict CSP; servers only on `127.0.0.1` with a token; arguments as a vector, never a line for the shell; validated names; downloads with a checksum or signature; secrets never in the logs.

## Startup

`main.rs`: command line read → kit root → creation of `data\`, write check, kit move (`root.txt`) → log, one folder per version (`versions::migrate`), versions side by side, cleanup of the old copy of the exe, app version → Gemini key out of `settings.json` (`settings::move_secrets`) → settings → disk that runs no program: stop (D-105) → certificate bundle (`net::ca::refresh`) → kit environment, applied to the process → files in `data\kit\` → if there is a command, it runs it and exits → single instance (D-08) → migration of the projects' data, Nginx pools and sites to Caddy (`servers::migrate`, D-120), temp cleanup (stale folders only set aside, D-182) → WebView2 (or WebKitGTK on Linux) → Job Object, or guard on macOS and Linux → `main` window with the theme of the settings → in the background the deletion of the set-aside temp folders and the kept conda packages (`install::conda::sweep`, under the preparation lock, D-182), the databases and the pools marked "Start with Atollo" (the pools not while the VM is on, D-175); installation of the missing required components and of the editor of another release (not before the first start's choice, D-137), and Docker Sandboxes again every hour while a failed installation left the kit without it (`isolation::install_failure`, D-175); pending Antigravity sign-in, Git helper and identity (`github::sync_git`), agent sync, agent watcher; version lists after 10 s and update check after 20 s (neither with `ATOLLO_NO_UPDATE`). At shutdown and before "Remove the drive", `isolation::stop_daemon` stops the daemon of the kit's Docker Sandboxes (`app\mod.rs`, `ipc\window.rs`).

## Rust engine (`tauri\src`)

A single binary, `Atollo.exe`: the window (Tauri 2) and the command line (`app\cli.rs`). Only `main.rs` stays at the top; everything else is in one folder per area (D-87, D-166). They read by layers: a layer above calls the one below, never the reverse.

| Layer | Modules | What they do |
| --- | --- | --- |
| Startup | `main.rs`, `app\` | startup order ("Startup", above), the app and its windows, the tray, the command line |
| IPC | `ipc\` | the interface's only entry point: the commands (they check the window, translate the errors, call the domain) and the names of the events Rust sends (`ipc\events.rs`) |
| Domain | the folders per area (below) | components, versions, projects, editor and console, agents, local models, databases, web servers, GitHub, isolation, diagnostics |
| Infrastructure | `common\`, `kit\`, `env\`, `net\`, `router\` | files, log, clock, languages, settings, ports; kit paths; environment; network and checks; target operating systems |
| Platform | `platform\` | the abstract layer over the operating system: the same API on Windows, macOS and Linux (below) |
| Systems | `os\windows\`, `os\unix\`, `os\macos\`, `os\linux\` | the code of each system, behind `platform\` only |

### The operating system (`platform\` and `os\`)

The engine looks at which system it is built for only in `os\` (D-166): everywhere else there is no `#[cfg(windows)]`, `#[cfg(unix)]`, `#[cfg(target_os = …)]` or `cfg!(…)`, no crate of one system (`libc`, `windows`, `webview2_com`, `junction`, `portable_pty`, `rfd`, `dbus_secret_service`) and no `std::os::<system>`. `test\rust\os\rule.rs` checks it, comments and strings left out.

- **`platform\`** is the API the engine calls, the same on every system, with the logic that is the same everywhere: `jobs` (the programs the kit starts, none outliving the app: D-07, D-105; the system shell and its quoting), `processes`, `sessions` (the kit's programs open, other kits, "Remove the drive"), `instance` (one app per kit, D-08), `lock` (the kit's locks across its processes: the preparation, `db.json`), `volume` (the disk of a folder, D-90, D-105), `temp` (`TempWork`, the folders in transit, D-90), `safe_path` (reading inside a project without following links, D-77), `files` (owner-only files and folders, the executable bit, private writes), `links` (junctions on Windows, symbolic links elsewhere), `host` (what the app knows of the machine: processor, language, build of Windows, os-release, Xcode, ICU, the AppImage), `desktop` (the "Select folder" and "Open" windows, the error box, the tray), `console` (the command line's output), `pty` (a program on a pseudo terminal, for the app's terminal), `proxy` (the system's proxy and the hosts reached without one), `signature` (Authenticode, Windows), `sockets` (whether a server answers on a Unix socket), `webview` (D-05), `virt` (what the PC lacks for Docker Sandboxes' microVMs: Windows 11 and Hypervisor Platform, Apple silicon and macOS 14, Ubuntu 24.04 and KVM; D-167), `memory`, `random`, `registry` (the current user's registry, Windows), `local_time`, and in `mod.rs` `OS`, `PATH_SEPARATOR`, `sh_quote`. Nothing there looks at which system it is: each function hands over to the module of the same name of `crate::os::current`, and the build of each system checks the signatures.
- **`os\windows\`** has Win32, WebView2, the ConPTY (`conpty.rs`), the registry, the Job Object; **`os\unix\`** what macOS and Linux share (process groups and the guard, `guard.rs`, D-105; `flock`; modes and owners; the instance's socket and TCP fallback; portable-pty; the gentle stop); **`os\macos\`** and **`os\linux\`** what only one has (libproc and `/proc`, `statfs` and `mountinfo`, `scutil` and `gsettings`, AppleLanguages, the AppImage, `PR_SET_PDEATHSIG`). `virt.rs` is in `windows\`, `macos\` and `linux\`, each with its own way of reading, without an administrator, what Docker Sandboxes needs (Windows 11 and the Hypervisor Platform via `WHvGetCapability`; macOS 14 on Apple silicon; Ubuntu 24.04, `/dev/kvm` and the AppArmor profile of the kit's shim). `macos\` and `linux\` re-export the `unix\` modules they share, so every system offers the same names; `os\mod.rs` is the only place that picks the system (`current`), and a build for another system stops with a `compile_error!`. `test\rust\os\rule.rs` also checks that every module `platform\` asks `os::current` for is there in `windows\`, `macos\` and `linux\`.

To add something that differs between the systems: the function, with its doc, in the module of `platform\` it belongs to (a new module if none fits, listed in `platform\mod.rs`), handing over to `imp::<name>`; the same function in `os\windows\<module>.rs` and in `os\unix\<module>.rs` (or in `os\macos\` and `os\linux\` when they differ); the module named in each `mod.rs` of `os\`. A pure parser of one system's text (`/proc`, `mountinfo`, `scutil`) goes in that system's folder, with its tests in `test\rust\os\<system>\`; what the engine compares on every system (a kit for another target) stays in its area, where the kit's target (`kit.os()`) decides, not the system the app runs on. A check of the system the app runs on, at run time, reads `platform::OS`.

### Isolation (`isolation\`) and the three levels (`levels\`)

Atollo's core is the portable configurator of Docker Sandboxes (`sbx`, D-167…D-178): each project gets a microVM whose shape Atollo writes and keeps in the kit. Only the kit's `sbx` is used (the `sandboxes` component, `data\apps\<target>\sandboxes\bin\sbx`, `isolation::kit_sbx`; `Sbx` is a struct around its path): one installed on the PC is never used, and the daemon of another `sbx` is never stopped (the `foreign_daemon` reason, D-175). Whether the VM is there is not a setting: `isolation::status` works it out (at most once a minute, or on "Check again") and the status bar's pill shows "VM" or "No VM".

**Where every program runs is decided in one place, `levels\` (D-179).** The normative description is [LEVELS.md](LEVELS.md): the constraint table, `decide`'s rules, the IPC, the entry points, the flows, the tests. In short:

| Level | What | With the VM | Without the VM |
| --- | --- | --- | --- |
| **1 Manual** | the kit's terminals and the editor's integrated terminal | on the PC, sealed except the user's SSH agent (`SSH_AUTH_SOCK`); `claude`, `codex`, `pi`, `agy` are forwarders (`data\kit\forward`) that ask the app to run the agent in the project's VM | on the PC; the forwarders say why and exit 1 |
| **2 Project code** | the project's terminal, actions, sites, Web Server pools, editor tasks, project creation | on the PC, sealed (`levels::env::seal`), as without the VM (D-183) | on the PC, sealed, "No VM" in the status bar; no agent on `PATH` |
| **3 Agents** | Claude Code, Codex, Pi and Antigravity, all in the project's sandbox `atollo-p-…` with their kit's builds for Linux (D-184) | only there | refused: everything that would start, install or offer an agent is disabled with the reason; the editor's extensions that run an agent are uninstalled at every editor start |

The code: every entry point builds a `levels::Request` (its `Origin` and the `Place` from `place_of`), reads `levels::facts`, and `levels::decide` (pure, rules R1–R8) returns a `Placement`: `Pc` (started with `levels::env::environment`), `Vm` (made ready by `levels::prepare`: the kit's Linux tools mounted read-only, the project's databases and ports, `info.json`, the sandbox started; then `levels::start`), or `Refused` with its reason and fix. The processes outside the app (the editor's profiles, the forwarders) ask through request files in `data\app\levels\requests\` with the clients `launch.ps1`/`launch.sh` (`levels::requests`, served by `ipc::levels::serve_requests`). `levels::agents` gates everything about agents on the VM; `levels::report` gives the project's «VM del progetto» panel (`ui\src\projects\vm.tsx`) and `atollo vm <project>` (`app\vmcli.rs`): each sandbox's state, mounts, ports and sessions, «Verifica strumenti», and the actions «Riavvia», «Ricrea», «Aggiorna strumenti». Inside every sandbox a read-only folder (`data\app\sandboxes\<sandbox>\guest\`) gives a read-only `atollo` (where you are, what you have) and the agents' stand-ins. No kit secret enters a VM: GitHub (D-172) and the Gemini key (Antigravity) only through `sbx`'s proxy secrets for that sandbox (LEVELS.md §11).

`isolation\` keeps what is about `sbx` itself:
- `mod.rs`: `status` (the availability, `isolation::Level { Vm, Env }`, and the `Blocker`s, in order: the system, the hypervisor and AppArmor from `platform::virt`, the kit's `sbx` (`sbx_missing`, with the reason of the last failed installation), the kit's disk (`kit_disk`), the daemon (`foreign_daemon`), `sbx ls --json` (`sbx_signed_out`, `sbx_failed`; a kit daemon older than the kit's `sbx` is restarted, then asked again), the network policy `sbx policy init balanced`), `Blocker::explain` and `why_no_vm`, `Sbx` (`find`, `command`, `session_env`), `Fix` and `fix_launch` ("Run" for `sbx login` and `sbx ls` in the app's terminal), the `Vm` of a sandbox (start with its kit, made again when the kit moved, read-only mounts added with `sbx mount` to a sandbox made before, database ports, the Gemini secret), `agent_in_vm`, `db_in_vm`, the sandboxes' list, stop and removal, `legacy_sandboxes` (the `atollo-t-` and `atollo-a-` sandboxes of an earlier Atollo), `stop_daemon`, `restart_pending`;
- `vm.rs`: pure builders of `sbx`'s arguments and names (`name`: `atollo-p-` and 96 bits of SHA-256; `start_args`, `agent_session_args` with `agent_vars`, `check_args`, `mount_args`, `host_port_allow`/`host_port_close`, `guest_target`, `guest_path`);
- `daemon.rs`: whose the daemon is, its state in the kit's home, `ENV`, `SETTINGS` (`ssh.agentForwardingEnabled=false`, `browser.enabled=false`, `diagnostics.autoUpload=no`);
- `kit.rs`: each sandbox's kit in `data\app\sandboxes\<sandbox>\` (`spec.yaml`, `atollo.json`, `.applied`, `.mounts`, `.ports`, `guest\`), its owner, the list and the removal;
- `secrets.rs`: `Atollo.exe secret github|gemini` registered per sandbox with `sbx secret set … --sandbox <vm> --command …`, answered only to the kit's `sbx` with a known nonce (`secrets.json`);
- around it: `platform\virt.rs` and `os\*\virt.rs` (`Gap`: what the PC lacks), `install\sandboxes.rs` (the component), `ipc\isolation.rs` (`isolation_status`, `vms_list`, `vm_remove`, `isolation_run`), `ui\src\shell\isolation.tsx` (the pill, the "No VM" dialog), the runner's `Scope` with `ipc::setup::vm_tools_target` (D-173, D-183), `kit\backup.rs` (`left_out`: the daemon's state stays out of "Copy of the kit").

Where a change goes:
- a new program, terminal or entry point → a `levels::Origin` and its rows in LEVELS.md (§2, §3.4, §5), through `decide`; never a `Command::new` of its own (the rule test `no_process_outside_levels`);

Folder rules:
- a module named after its area is the folder's `mod.rs` (`editor\mod.rs`, not `editor\editor.rs`: clippy rejects it), so `crate::editor::Editor` and `crate::versions::*` stay short; folders without logic of their own (`db\`, `setup\`, `common\`) hold only the description of the area in `mod.rs`;
- every `mod.rs` starts with a `//!` that names the area and its submodules;
- paths are written in full (`crate::setup::task::SetupTask`, `use crate::db::auth;`), without aliases and without `pub use x::*`; within the same folder `use super::x;`. What the whole crate reads from a folder is re-exported by name in its `mod.rs` and written with the short path: `crate::setup::{Catalog, Component, Choice, Group, kit_path}`, `crate::router::{write_private, write_executable, set_executable, restrict_to_owner, restrict_dir_to_owner}`;
- a module split into files (`db\services\`, `versions\relations\`, `projects\frameworks\`, `install\lang\`, `servers\`) re-exports in `mod.rs` only what is used from outside; its files call each other with `pub(super)` and are imported by name (`use super::pools::load_store;`), never with `use super::*`; the methods of a type can also live in several files, with one `impl` per file (`servers\`: `WebServers`);
- a file is split when it has parts that read on their own; `projects\run\` is a folder, one file per part of the runner (STR-V7-02), and `env\` one per part of `KitEnv::build`, which calls a function per section in order (STR-V7-03). Files should stay under 900 lines; today only `isolation\mod.rs` (about 1,500) is over (below, "Opportunities"). The Guide's texts (`guide\content\`) are text, not code.

### Kit files (`common\fsx.rs` and `Kit`)

Every module follows the same rules for its files in `data\`:

- **paths** from the methods of `Kit` (`data()`, `apps()`, `app_dir()`, `settings_file()`, `versions_dir()`, `versions_root()`, `old_root_file()`, `project_data()`, `system_temp()`…; the files of a project from `projects::state::ProjectState`) or from a function of the module that owns the file (`db::services::settings_path`, `versions::offered_file`); never the same file name written in two modules;
- **reading**: `fsx::read_text` (UTF-8 with replacement of invalid bytes, without BOM); for JSON `fsx::read_json` (missing or damaged: `None`, for state the kit rebuilds), `fsx::load_json` (the default value plus the problem to show, for the user's settings) or `fsx::try_read_json` (error with the path). An empty file counts as missing;
- **writing**: `fsx::write_json` (creates the folder, indented JSON, atomic) or `fsx::write_atomic` for text; never `fs::write` on a file the kit reads back;
- **files of other programs** (editor settings, agent files, `.mcp.json`) as `serde_json::Value`, with the rules of their module: a file with comments or an invalid one is not overwritten;
- **inside a project** only with `platform::safe_path` (no link followed, D-77).

### One change at a time (locks)

A file that several threads change is read, changed and written under one lock, so no change is lost; a slow operation has its own lock, taken before the file's, never the other way round.

| What | Lock | Covers |
| --- | --- | --- |
| `settings.json` | `Settings::update` (D-137) | the Settings page, "Platform" of Tools, the installations; `apply_env` rebuilds the environment under a lock of its own, from the file as it is then |
| a project's `dev-settings.json` | `projects::settings::update` | |
| `services.json` | `update_settings` in `db\services\mod.rs` (D-140) | every read-modify-write: `keep_port`, `set`, `set_line_port`, `set_line` |
| a database server | `Services::op(engine)`, one per engine (D-140) | start, stop and change of version: two starts of the same version start one server and give the same port; two versions of one engine start in turn. `stop_all`, at shutdown, does not take it. Order: operation → `running`/`errors` → `services.json` |
| `servers.json` and the pools | `WebServers`: `op_lock` → `store_lock` → `running` (`servers\mod.rs`) | start, stop and reload; every change of `servers.json` (ports, profiles) |
| `terminals.json` | `STORE` in `editor\terminals.rs` | |
| `llm.json` | `llm::settings::update` | port, automatic start, Pi's model |
| the local models' server | `Llm::op` (`llm\service.rs`, D-151) | one operation at a time: start, stop, restart after a download, stop while a model is deleted; `stop_all` ("Stop all", "Remove drive", shutdown) does not take it. Order: operation → `running` → `error` |

The logins of the database tools (dumps and restores) are files named `<exe>-<pid>-<seq>` (`db\services\tools.rs`): two backups at the same time never delete each other's.

### Ports

`common\ports.rs` (D-141) also has the two probes of a port, `responds` and `is_port_free` (IPv4 and IPv6 loopback), used by the actions, the database servers, the local models and the pools. It tells who has each port, from the files only and without taking any lock, so whoever already holds its own can ask:

| Owner (`Owner`) | From | Range |
| --- | --- | --- |
| `Pool` | `servers.json` (`servers::pool_ports`) | automatic, or the profile's |
| `Db` (engine and version) | `services.json`: the server's port, `line_ports` of the installed versions, the ports kept for the uninstalled ones | 3306, 27017 and the next ones |
| `Project` (project → action) | the `ports.json` of each project (`projects::run::saved_ports`) | 7100-7999 |
| `Editor` | `editor::PORTS` | 7000-7099 |
| `Llm` | `llm\settings.rs` (`data\app\llm.json`) | 9931-9999 (`llm::settings::PORTS`) |

`ports_taken` gives the whole map; `refuse_taken(kit, port, own, lang)` fails with the owner named ("Port {0} already belongs to …") unless the owner is the entry being saved. It is called by `WebServers::save_profile` (a profile's port), `Runner::set_port` (an action's port chosen by hand), `Services::set` and `Services::set_line_port` (a server's or a version's port, before `update_settings`); `assign_or_get_port` gives a new pool none of the taken ports. Every database version keeps its own port: it is saved at its start and, for all the installed versions, when the server's version changes (D-140).

### Local hosts and the project's `conf.d`

- The static file server (`projects\serve.rs`, `is_local_host_header`) and `php -S` (`runtime\php-router.php`) answer `localhost`, `*.localhost`, `127.0.0.1` and `[::1]`; with "Local network" (`ATOLLO_ALLOW_LAN=1`) also a literal IP address, so the other devices of the network reach them by the PC's IP. Any other name gets 403 from the file server and 421 from `php -S` (DNS rebinding cannot read the project).
- `data\projects\<p>\apache\conf.d\*.conf` and `caddy\conf.d\*.caddy` hold the user's own directives. The dedicated Apache includes them (`IncludeOptional`), and so does the site's vHost in an Apache pool (`servers\config.rs`); the project's own Caddy (`projects::caddy::project_conf`) and a Caddy pool import them only when the folder has a `.caddy` file (`caddy::has_snippets`: an `import` that matches nothing stops Caddy). A folder written into `httpd.conf` or a Caddyfile goes through `apache::quoted_path` or `caddy::quoted_path`, which refuse a name with `"`, `\`, a line break or `${` (the folder is then not served): a cloned repository's folder name never becomes a directive (BUG-V7-09).

### Processes

All the kit's programs start in the app's Job Object (Windows) or in process groups watched by the guard (macOS, Linux) with the kit's environment (`platform\jobs.rs`, D-07, D-105). Only the browser and the file manager run outside: `jobs::open_with_explorer` opens a folder, `jobs::open_url` an address, both with the PC's environment read at startup (`Host::capture`, D-169). No `Command::new` with a joined command line: arguments always as a vector. The kit's `sbx` is one of the kit's programs too (`Sbx::command`, through `platform::jobs::kit_command`); a program inside a VM is not: closing its `sbx exec` on the PC does not stop it, so an action notes its process group in the VM and its stop goes in there (`Vm::stop_run`, D-175).

### Errors

In the modules `anyhow::Result`, with the context the log needs. Commands return `CmdResult<_>` (`ipc\error.rs`): `CmdError` is the short text the interface shows and arrives as a JSON string, the same as that of `Result<_, String>`. A command reports an error in four ways:
- `.or_fail(context)?` writes `context: error` to the log and sends `error` to the interface (`{e}`); `.or_fail_chain(context)?` does the same with the whole chain of an `anyhow::Error` (`{e:#}`);
- `?` on an `anyhow::Error` sends the whole chain without writing to the log;
- `Err(text.into())` for a refusal with a text for the user, which goes through `tr`/`i18n::t` with the Italian sentence as the key;
- `return Err(fail(context, error))` when the log is needed without a `Result` to start from.

### `ipc\`

- `core.ts` has the three helpers every command is written with: `query(cmd, preview, args)` for a command that answers with data, `act(cmd, args)` for one that just acts, `subscribe(event, handler)` for events. Outside Tauri (`npm run dev` opened in the browser) they answer with the preview and the page shows the "preview" banner: this way the pages render in the browser. They stay inside `ipc\`: pages do not call commands by name.
- A computed preview (`sampleStats()`) is written as `browserPreview ? … : invoke(…)`, so that it is not computed when the app is running.
- The types mirror the Rust structs with `serde(rename_all = "camelCase")`.

### Hooks (`shared\hooks.ts`)

- `useSubscription(onRun, handler)` registers a listener only once, passes every event to the latest `handler` and removes it on unmount even if the registration finishes later.
- `useEvery(read, ms)` reads right away and then every `ms`; `read` must be kept stable with `useCallback`.
- `useLoad(load, initial, { onError, every, enabled, key })` gives `{ data, error, reload, setData }`: it reads on mount, when `load` (stable with `useCallback`) or `key` changes, every `every` ms, and on every `reload`. With `enabled: false` it does not read. `onError` says what a failed read does: `"keep"` leaves the value as it was, `"show"` leaves it and puts the text in `error` (cleared by the next successful read), `{ fallback }` sets the fallback value. After unmount it writes nothing.
- `useAction(onDone)` runs an action with the wait state and the last error.
- `useCopy(resetMs)` copies to the clipboard; `copied` goes back to false after `resetMs`, if given.

Reads still written by hand, because `useLoad` would change what the user sees: an error that stays even after a successful read (`App.tsx` for the information, `shell\eject.tsx`, `settings\page.tsx`, `databases\page.tsx`, where the same error also covers start and stop); chained reads or reads that fill a form (`components\page.tsx`, `projects\editorsettings.tsx`); reads with arguments or with their own requests and wait state (`frameworks\model.ts`, `github\repos.tsx`, `components\relations.tsx`, `agents\stats.tsx`, `components\setup.tsx`).

### `workbench\`

The controls are VSCodium's: `@vscode-elements/elements` (D-88), registered once in `elements.ts` with their ES modules, never with `dist/bundled.js` (the React wrappers import the same modules). Pages use only the components of `workbench\`, with the same props as before. The controls are in `buttons.tsx`, `inputs.tsx` and `indicators.tsx` (what fields and buttons share in `fields.ts`, not exported); `index.ts` exports them all.

| Component | Drawn with |
| --- | --- |
| `Button` | `vscode-button` (secondary, wide, small); with `submit` a hidden `<button type=submit>` next to it remains the form's default button, so Enter in a field submits |
| `TextField`, `TextArea`, `SearchBox` | `VscodeTextfield`, `VscodeTextarea` (wrappers from `@vscode-elements/react-elements`); value controlled with `useControlled` |
| `Select` | `VscodeSingleSelect` + `VscodeOption`; groups become a disabled header option |
| `CountBadge`, `ProgressBar`, `Divider` | `vscode-badge`, `vscode-progress-bar`, `vscode-divider` |
| `Codicon`, `codicon(name)` | the Codicon font of `@vscode/codicons` in the page, as the workbench draws it (`<span class="codicon codicon-NAME">`, 16 px or the compact 12 px from the tokens); `codicon(name)` makes it an icon component where a control takes one (`IconButton`, `ActionButton`, lists, pages) |
| `Icon` | `vscode-icon`, only for a spinning codicon |
| `SettingItem` | `vscode-form-group` with the "settings-group" variant |
| `IconButton`, `Checkbox`, `CheckboxLabel`, `Radio` | native, drawn like `vscode-toolbar-button`, `vscode-checkbox`, `vscode-radio` with their variables: in the components the button or the box sits in the shadow root, where `<label for>`, the click on the label and the roles the tests look for do not reach, and `vscode-toolbar-button` has no disabled state |
| `DataTable` | native `<table>`, drawn like `vscode-table`: the component has no caption or row headers and splits the columns into equal parts |
| `ConfirmDialog`, `InlineConfirm` | own dialog, `vscode-button` buttons |
| parts (`layout.tsx`: panes, tabs, details bar, panel), lists (`list.tsx`), Settings editor (`settings.tsx`) | own: `vscode-collapsible` and `vscode-tabs` draw the classic headers, not the modern ones of VSCodium 1.135, and keep roles and `tablist` in the shadow root |

Rules for whoever adds a control:
- fields and selects send a `change` that does not bubble: React's `onChange` on a hand-written `<vscode-*>` tag never fires. Use the wrappers (`VscodeTextfield`…) or a `workbench\` primitive;
- on a hand-written `<vscode-*>` tag write `class` and `for`, not `className` and `htmlFor`; the JSX types are in `elements.ts`;
- an icon is a codicon (`Codicon` or `codicon(name)`); `react-icons` gives only the brand logos (`shared\logos.tsx`, Simple Icons) and the `IconType` type, and nothing imports `react-icons/vsc` (a test checks it);
- `vscode-icon` needs the codicon CSS with the id `vscode-codicon-stylesheet` (`elements.ts` adds it, disabled in the page) and takes its color from `--vscode-icon-foreground`: for the color of the surrounding text, `[--vscode-icon-foreground:currentColor]`;
- a color always comes from a theme variable (`--vscode-*` or a `vsc-*` token), never written by hand; the exceptions are VSCodium's fixed values (the red of the Close button) and the logo colors;
- a measure (height, width, padding, radius, shadow) always comes from `theme-sizes.css`: a `--vscode-*` size of VSCodium's registry or a `--vsc-size-*` token with its utility (`h-vsc-*`, `w-vsc-*`, `size-vsc-*`), never a number written in a component (D-142).

These stay native, with the reason in the file: the window buttons (`shell\titlebar.tsx`), activity bar and status bar (`App.tsx`), the agent choice with the logos (`agents\page.tsx`, `radio` role), the locked menu button in `versions\kit.tsx`. Since October 21, 2026 the workbench also has `ToggleButton` (text and `aria-pressed`, the wizard's choices), `Meter` (`meter` role with a value, the limits in `agents\stats.tsx`) and `SuggestField` (`workbench\suggest.tsx`, a `TextField` with the suggestion list drawn under it, replacing the `<datalist>` of `projects\extensions.tsx`, which does not cross the shadow root). `workbench\elements.ts` registers only the `vscode-elements` components in use, each from its own module; `elements.test.tsx` checks that every tag drawn is registered.

Tests: `test\ui\workbench\controls.test.tsx` (events that really fire, controlled values, Enter, accessible names), `elements.test.tsx` (registration), `codicon.test.tsx` (glyphs of the bundled font, sizes, no `react-icons/vsc`), `layout.test.tsx`, `list.test.tsx`, `dialog.test.tsx`, `settings.test.tsx`. jsdom has no `adoptedStyleSheets`: `test\ui\setup.ts` provides an empty version of it, which draws nothing.

### Theme

A single source: `docs\brand\themes.py` resolves VSCodium's Dark Modern and Light Modern (`docs\brand\vscodium-themes\`) with the Atollo accent and writes four outputs.

- `tauri\editor-theme\`: the editor's "Atollo Dark" and "Atollo Light" themes;
- `ui\src\theme\theme-vscode.css`: for each theme about 800 `--vscode-*` variables, as VS Code gives them to its webviews, with the Windows fonts. The values, from weakest to strongest: the tables in `docs\brand\vscode-defaults\` (from `@vscode-elements/webview-playground` 1.9.0, MIT license), `BUILTIN`, `DERIVED` (the colors VS Code computes from a key changed by the brand, checked against the tables), the whole editor theme. Names as in the webviews: only the first dot becomes `-`;
- `ui\src\theme\theme-colors.css`: the `--vsc-*` color tokens for Tailwind, each one a `var(--vscode-…)`;
- `ui\src\theme\theme-sizes.css`: the sizes of VSCodium's registry (`--vscode-spacing-size*`, `--vscode-cornerRadius-*`, font sizes and weights, the modern UI's shadows), the workbench's own measures (`--pane-header-size`…) and the app's `--vsc-size-*` measures with their Tailwind utilities, the same in every theme.

The theme files come from a newer VSCodium than the one the kit ships: `RENAMED` gives their keys the names 1.135 reads, so the activity bar's item colors are `modernActivityBar.*`, in the app and in the editor theme alike. The sizes come from `docs\brand\vscodium-1.135\workbench-ref.css`, the part of VSCodium 1.135's workbench CSS the app mirrors (D-142), with the MIT license of Code-OSS: `node scripts/vscodium-css/extract.mjs` writes it from the editor's archive pinned in `components.json` (downloaded and checked with its SHA-256, or a path to an archive or to an extracted `workbench.css`) and fails on a `--vscode-*` key the app reads that this VSCodium does not know.

This way the app and the editor have the same colors and measures, key by key. A color is changed in `themes.py` (in `BRAND`), a measure in `LAYOUT`, then `python docs/brand/themes.py`; when the catalog pins another editor, first `extract.mjs`. `test\ui\theme\theme.test.ts` checks that every variable read by the components is defined in both themes, that every size is declared once with its utility, that the sizes are those of `workbench-ref.css`, that no token of the classic UI's parts is left and that VSCodium knows every `--vscode-*` key Atollo reads.
