# Code architecture

English · [Italiano](ARCHITECTURE.it.md)

How Atollo's code is organized and where a new change goes. The reasons behind the choices are in [DECISIONS.md](DECISIONS.md) (in Italian), usage in the [Guide](https://nabre.github.io/atollo/guide/), what is new in [CHANGELOG.md](CHANGELOG.md) (in Italian), tests in [TESTING.md](TESTING.md). Open work is in the [GitHub issues](https://github.com/nabre/atollo/issues).

## Requirements

From the initial prompt (October 13-14, 2026), valid for every change; each one has a test or an item in the TESTING.md checklist.

1. **No installation**: a single executable (on macOS the `.app` bundle, on Linux the AppImage), no installer, service or scheduled task.
2. **No administrator rights** (`asInvoker` manifest on Windows).
3. **No writes outside the kit**: no registry, system `PATH`, real `%APPDATA%`, `%LOCALAPPDATA%` or `%TEMP%`; the only exceptions are the ones declared in the README (D-41, D-70, D-90, D-115).
4. **Paths relative to the kit root**, which works from any folder (spaces, parentheses, `&`) and after a move (relocation at startup).
5. **WebView in the kit**: the system WebView2 or a fixed one in `data\apps\…\webview2\`, never the bootstrapper; WebView data in `data\webview2\` (on macOS it stays in `~/Library/WebKit`, a declared trace).
6. **Always the kit's environment**: every process started gets the environment from `env\`, never the user's `PATH` unfiltered.
7. **A single instance per kit**, with a notice about the other open copies.
8. **No orphan processes**, even if the app is force-closed (Job Object on Windows, groups and a guard on macOS and Linux: D-07, D-105).
9. **Security**: Tauri commands only for the `main` window, editor windows without IPC, strict CSP; servers only on `127.0.0.1` with a token; arguments as a vector, never a line for the shell; validated names; downloads with a checksum or signature; secrets never in the logs.

## Startup

`main.rs`: command line read → kit root → creation of `data\`, write check, kit move (`root.txt`) → log, one folder per version (`versions::migrate`), versions side by side, cleanup of the old copy of the exe, app version → Gemini key out of `settings.json` (`settings::move_secrets`) → settings → disk that runs no program: stop (D-105) → certificate bundle (`net::ca::refresh`) → kit environment, applied to the process → files in `data\kit\` → if there is a command, it runs it and exits → single instance (D-08) → migration of the projects' data, Nginx pools and sites to Caddy (`servers::migrate`, D-120), temp cleanup, kept conda packages (`install::conda::sweep`) → WebView2 (or WebKitGTK on Linux) → Job Object, or guard on macOS and Linux → `main` window with the theme of the settings → in the background the databases and the pools marked "Start with Atollo"; installation of the missing required components and of the editor of another release (not before the first start's choice, D-137); pending Antigravity sign-in, Git helper and identity (`github::sync_git`), agent sync, agent watcher; version lists after 10 s and update check after 20 s (neither with `ATOLLO_NO_UPDATE`).

## Rust engine (`tauri\src`)

A single binary, `Atollo.exe`: the window (Tauri 2) and the command line (`app\cli.rs`). Only `main.rs` stays at the top; everything else is in one folder per area (D-87, D-166). They read by layers: a layer above calls the one below, never the reverse.

| Layer | Modules | What they do |
| --- | --- | --- |
| Startup | `main.rs`, `app\` | startup order ("Startup", above), the app and its windows, the tray, the command line |
| IPC | `ipc\` | the interface's only entry point: the commands (they check the window, translate the errors, call the domain) and the names of the events Rust sends (`ipc\events.rs`) |
| Domain | the folders per area (below) | components, versions, projects, editor and console, agents, local models, databases, web servers, GitHub, diagnostics |
| Infrastructure | `common\`, `kit\`, `env\`, `net\`, `router\` | files, log, clock, languages, settings, ports; kit paths; environment; network and checks; target operating systems |
| Platform | `platform\` | the abstract layer over the operating system: the same API on Windows, macOS and Linux (below) |
| Systems | `os\windows\`, `os\unix\`, `os\macos\`, `os\linux\` | the code of each system, behind `platform\` only |

### The operating system (`platform\` and `os\`)

The engine looks at which system it is built for only in `os\` (D-166): everywhere else there is no `#[cfg(windows)]`, `#[cfg(unix)]`, `#[cfg(target_os = …)]` or `cfg!(…)`, no crate of one system (`libc`, `windows`, `webview2_com`, `junction`, `portable_pty`, `rfd`, `dbus_secret_service`) and no `std::os::<system>`. `test\rust\os\rule.rs` checks it, comments and strings left out.

- **`platform\`** is the API the engine calls, the same on every system, with the logic that is the same everywhere: `jobs` (the programs the kit starts, none outliving the app: D-07, D-105; the system shell and its quoting), `processes`, `sessions` (the kit's programs open, other kits, "Remove the drive"), `instance` (one app per kit, D-08), `lock` (the kit's locks across its processes: the preparation, `db.json`, Antigravity's sign-in), `volume` (the disk of a folder, D-90, D-105), `temp` (`TempWork`, the folders in transit, D-90), `safe_path` (reading inside a project without following links, D-77), `files` (owner-only files and folders, the executable bit, private writes), `links` (junctions on Windows, symbolic links elsewhere), `host` (what the app knows of the machine: processor, language, build of Windows, os-release, Rosetta, Xcode, ICU, the AppImage, the machine id), `desktop` (the "Select folder" and "Open" windows, the error box, the tray), `console` (the command line's output), `pty` (a program on a pseudo terminal, for the app's terminal), `proxy` (the system's proxy and the hosts reached without one), `signature` (Authenticode, Windows), `sockets` (whether a server answers on a Unix socket), `webview` (D-05), `memory`, `random`, `registry` (the current user's registry, Windows), `local_time`, and in `mod.rs` `OS`, `PATH_SEPARATOR`, `sh_quote`. Nothing there looks at which system it is: each function hands over to the module of the same name of `crate::os::current`, and the build of each system checks the signatures.
- **`os\windows\`** has Win32, WebView2, the ConPTY (`conpty.rs`), the Credential Manager and DPAPI (`agy_store.rs`), the registry, the Job Object; **`os\unix\`** what macOS and Linux share (process groups and the guard, `guard.rs`, D-105; `flock`; modes and owners; the instance's socket and TCP fallback; portable-pty; the gentle stop; the sealing key of Antigravity's sign-in); **`os\macos\`** and **`os\linux\`** what only one has (libproc and `/proc`, `statfs` and `mountinfo`, `scutil` and `gsettings`, the Keychain and the Secret Service in `agy_keyring.rs`, AppleLanguages, the AppImage, `PR_SET_PDEATHSIG`). `macos\` and `linux\` re-export the `unix\` modules they share, so every system offers the same names; `os\mod.rs` is the only place that picks the system (`current`), and a build for another system stops with a `compile_error!`. `test\rust\os\rule.rs` also checks that every module `platform\` asks `os::current` for is there in `windows\`, `macos\` and `linux\`.

To add something that differs between the systems: the function, with its doc, in the module of `platform\` it belongs to (a new module if none fits, listed in `platform\mod.rs`), handing over to `imp::<name>`; the same function in `os\windows\<module>.rs` and in `os\unix\<module>.rs` (or in `os\macos\` and `os\linux\` when they differ); the module named in each `mod.rs` of `os\`. A pure parser of one system's text (`/proc`, `mountinfo`, `scutil`) goes in that system's folder, with its tests in `test\rust\os\<system>\`; what the engine compares on every system (a kit for another target) stays in its area, where the kit's target (`kit.os()`) decides, not the system the app runs on. A check of the system the app runs on, at run time, reads `platform::OS`.

In the system temp, `<TEMP>\Atollo\<id>\` (D-90): `setup\<id>\`, `frameworks\<stamp>\`, `downloads\`, `phpmyadmin\`, `system\` and `claude\` (`TEMP` of the programs and `CLAUDE_CODE_TMPDIR`, when the choice or the disk calls for it). `Kit::system_temp()` returns it, `platform\temp.rs` creates its work folders and cleans them up, `net\archive.rs` (`stage_into`) moves the result into `data\apps`. The startup order: the migration of the projects' data (`projects\migrate.rs`) runs after the single instance (D-08), followed by the temp cleanup (`platform::temp::sweep`); at shutdown, after the job, `platform::temp::cleanup_at_exit`.

Folder rules:
- a module named after its area is the folder's `mod.rs` (`editor\mod.rs`, not `editor\editor.rs`: clippy rejects it), so `crate::editor::Editor` and `crate::versions::*` stay short; folders without logic of their own (`db\`, `setup\`, `common\`) hold only the description of the area in `mod.rs`;
- every `mod.rs` starts with a `//!` that names the area and its submodules;
- paths are written in full (`crate::setup::task::SetupTask`, `use crate::db::auth;`), without aliases and without `pub use x::*`; within the same folder `use super::x;`. What the whole crate reads from a folder is re-exported by name in its `mod.rs` and written with the short path: `crate::setup::{Catalog, Component, Choice, Group, kit_path}`, `crate::router::{write_private, write_executable, set_executable, restrict_to_owner, restrict_dir_to_owner}`;
- a module split into files (`db\services\`, `versions\relations\`, `projects\frameworks\`, `install\lang\`, `servers\`) re-exports in `mod.rs` only what is used from outside; its files call each other with `pub(super)` and are imported by name (`use super::pools::load_store;`), never with `use super::*`; the methods of a type can also live in several files, with one `impl` per file (`servers\`: `WebServers`);
- a file is split when it has parts that read on their own; `editor\ext.rs` and `editor\pty.rs` (the PTY sessions on every system, over 900 lines) stay whole; `projects\run\` is a folder, one file per part of the runner (STR-V7-02), and `env\` one per part of `KitEnv::build`, which calls a function per section in order (STR-V7-03). The other files should stay under 900 lines. The Guide's texts (`guide\content\`) are text, not code.

### IPC (`ipc\` and `ui\src\ipc\`)

Everything that crosses between the interface and Rust is in two folders with the same name: `tauri\src\ipc\` and `ui\src\ipc\` (D-166). The commands are one file per page or area of the interface, with the same names as the files in `ui\src\ipc\`; the events Rust sends have their names in `ipc\events.rs`, the same as in `ui\src\ipc\events.ts` (a Rust test compares the two files): who emits or subscribes uses the constant, never the string.

| File | Commands |
| --- | --- |
| `mod.rs` | `AppState`, the shared checks (`ensure_main`, `project_dir`, `tr`), `ensure` (installs what is missing before an action), the `command_handler!` macro |
| `error.rs` | `CmdError`, `CmdResult`, `fail` and `OrFail` (below, "Errors") |
| `events.rs` | the names of the events sent to the interface (`run`, `setup`, `pty-*`…) |
| `app.rs` | information, settings, updates, opening addresses and folders |
| `window.rs` | what is open, "Remove drive", shutdown and confirmation |
| `editing.rs` | editor, console, editor settings and extensions of a project |
| `setup.rs` | choice of components, installation in progress, downloads by hand |
| `versions.rs` | saved versions, project versions, relations matrix |
| `agents.rs` | status, consumption, launch and exit of the agents |
| `llm.rs` | local models: server status, start and stop, settings, catalog and models on disk, Hugging Face, downloads and their cancel, removal, the token and the key; one hand-written permission, `allow-local-models` (`permissions\llm.toml`), instead of one per command |
| `projects.rs` | list, creation, clone, deletion, actions, site, status, MCP |
| `orphans.rs` | data without a project: list and "Link to…" (D-89) |
| `frameworks.rs` | new project from a framework |
| `github.rs` | GitHub account and repositories |
| `databases.rs` | project databases, copies, `.env`, content, phpMyAdmin, mongo-express |
| `services.rs` | the kit's database servers |
| `servers.rs` | web server pools: list, profiles, start, stop, reload, linked project |
| `terminals.rs` | Terminals page: list, saving, removal, opening, folder choice; the in-app terminal's sessions |
| `runs.rs` | started actions: start, stop, output, ports |

To add a command:
1. the `#[tauri::command]` function in the file of its area, which returns `CmdResult<_>`, starts with `ensure_main(&webview)?` and calls the domain module (the logic stays there, the command translates it for the interface);
2. its path in `command_handler!` (`ipc\mod.rs`);
3. its name in `COMMANDS` (`build.rs`): the build generates `permissions\autogenerated\<name>.toml`;
4. `allow-<name>` in `capabilities\main.json`;
5. the TypeScript function in `ui\src\ipc\<area>.ts`, with the browser preview;
6. the new texts in the catalogs of the four languages (`tauri\i18n\catalog.json`, `ui\src\locales\*.json`).

A helper used by several areas (for example `apply_env`, `open_in_browser`) stays in the file of its area with `pub(super)` visibility and is imported by name in `mod.rs`. A new event: its constant in `ipc\events.rs` (and in `ALL`) and in `ui\src\ipc\events.ts`, the subscription in `ui\src\ipc\<area>.ts`.

### Kit files (`common\fsx.rs` and `Kit`)

Every module follows the same rules for its files in `data\`:

- **paths** from the methods of `Kit` (`data()`, `apps()`, `app_dir()`, `settings_file()`, `versions_dir()`, `versions_root()`, `old_root_file()`, `project_data()`, `system_temp()`…; the files of a project from `projects::state::ProjectState`) or from a function of the module that owns the file (`db::services::settings_path`, `versions::offered_file`); never the same file name written in two modules;
- **reading**: `fsx::read_text` (UTF-8 with replacement of invalid bytes, without BOM); for JSON `fsx::read_json` (missing or damaged: `None`, for state the kit rebuilds), `fsx::load_json` (the default value plus the problem to show, for the user's settings) or `fsx::try_read_json` (error with the path). An empty file counts as missing;
- **writing**: `fsx::write_json` (creates the folder, indented JSON, atomic) or `fsx::write_atomic` for text; never `fs::write` on a file the kit reads back;
- **files of other programs** (editor settings, agent files, `.mcp.json`) as `serde_json::Value`, with the rules of their module: a file with comments or an invalid one is not overwritten;
- **inside a project** only with `platform::safe_path` (no link followed, D-77).

### One change at a time (locks)

A file that several threads change is read, changed and written under one lock, so no change is lost; a slow operation has its own lock, taken before the file's, never the other way round.

| What | Lock | Covers |
| --- | --- | --- |
| `settings.json` | `Settings::update` (D-137) | the Settings page, "Platform" of Tools, the installations; `apply_env` rebuilds the environment under a lock of its own, from the file as it is then |
| a project's `dev-settings.json` | `projects::settings::update` | |
| `services.json` | `update_settings` in `db\services\mod.rs` (D-140) | every read-modify-write: `keep_port`, `set`, `set_line_port`, `set_line` |
| a database server | `Services::op(engine)`, one per engine (D-140) | start, stop and change of version: two starts of the same version start one server and give the same port; two versions of one engine start in turn. `stop_all`, at shutdown, does not take it. Order: operation → `running`/`errors` → `services.json` |
| `servers.json` and the pools | `WebServers`: `op_lock` → `store_lock` → `running` (`servers\mod.rs`) | start, stop and reload; every change of `servers.json` (ports, profiles) |
| `terminals.json` | `STORE` in `editor\terminals.rs` | |
| `llm.json` | `llm::settings::update` | port, automatic start, Pi's model |
| the local models' server | `Llm::op` (`llm\service.rs`, D-151) | one operation at a time: start, stop, restart after a download, stop while a model is deleted; `stop_all` ("Stop all", "Remove drive", shutdown) does not take it. Order: operation → `running` → `error` |

The logins of the database tools (dumps and restores) are files named `<exe>-<pid>-<seq>` (`db\services\tools.rs`): two backups at the same time never delete each other's.

### Ports

`common\ports.rs` (D-141) also has the two probes of a port, `responds` and `is_port_free` (IPv4 and IPv6 loopback), used by the actions, the database servers, the local models and the pools. It tells who has each port, from the files only and without taking any lock, so whoever already holds its own can ask:

| Owner (`Owner`) | From | Range |
| --- | --- | --- |
| `Pool` | `servers.json` (`servers::pool_ports`) | automatic, or the profile's |
| `Db` (engine and version) | `services.json`: the server's port, `line_ports` of the installed versions, the ports kept for the uninstalled ones | 3306, 27017 and the next ones |
| `Project` (project → action) | the `ports.json` of each project (`projects::run::saved_ports`) | 7100-7999 |
| `Editor` | `editor::PORTS` | 7000-7099 |
| `Llm` | `llm\settings.rs` (`data\app\llm.json`) | 9931-9999 (`llm::settings::PORTS`) |

`ports_taken` gives the whole map; `refuse_taken(kit, port, own, lang)` fails with the owner named ("Port {0} already belongs to …") unless the owner is the entry being saved. It is called by `WebServers::save_profile` (a profile's port), `Runner::set_port` (an action's port chosen by hand), `Services::set` and `Services::set_line_port` (a server's or a version's port, before `update_settings`); `assign_or_get_port` gives a new pool none of the taken ports. Every database version keeps its own port: it is saved at its start and, for all the installed versions, when the server's version changes (D-140).

### Local hosts and the project's `conf.d`

- The static file server (`projects\serve.rs`, `is_local_host_header`) and `php -S` (`runtime\php-router.php`) answer `localhost`, `*.localhost`, `127.0.0.1` and `[::1]`; with "Local network" (`ATOLLO_ALLOW_LAN=1`) also a literal IP address, so the other devices of the network reach them by the PC's IP. Any other name gets 403 from the file server and 421 from `php -S` (DNS rebinding cannot read the project).
- `data\projects\<p>\apache\conf.d\*.conf` and `caddy\conf.d\*.caddy` hold the user's own directives. The dedicated Apache includes them (`IncludeOptional`), and so does the site's vHost in an Apache pool (`servers\config.rs`); the project's own Caddy (`projects::caddy::project_conf`) and a Caddy pool import them only when the folder has a `.caddy` file (`caddy::has_snippets`: an `import` that matches nothing stops Caddy). A folder written into `httpd.conf` or a Caddyfile goes through `apache::quoted_path` or `caddy::quoted_path`, which refuse a name with `"`, `\`, a line break or `${` (the folder is then not served): a cloned repository's folder name never becomes a directive (BUG-V7-09).

### Processes

All the kit's programs start in the app's Job Object (Windows) or in process groups watched by the guard (macOS, Linux) with the kit's environment (`platform\jobs.rs`, D-07, D-105). Only the browser and the file manager run outside: `jobs::open_with_explorer` opens a folder, `jobs::open_url` an address. No `Command::new` with a joined command line: arguments always as a vector.

### Errors

In the modules `anyhow::Result`, with the context the log needs. Commands return `CmdResult<_>` (`ipc\error.rs`): `CmdError` is the short text the interface shows and arrives as a JSON string, the same as that of `Result<_, String>`. A command reports an error in four ways:
- `.or_fail(context)?` writes `context: error` to the log and sends `error` to the interface (`{e}`); `.or_fail_chain(context)?` does the same with the whole chain of an `anyhow::Error` (`{e:#}`);
- `?` on an `anyhow::Error` sends the whole chain without writing to the log;
- `Err(text.into())` for a refusal with a text for the user, which goes through `tr`/`i18n::t` with the Italian sentence as the key;
- `return Err(fail(context, error))` when the log is needed without a `Result` to start from.

### `ipc\`

- `core.ts` has the three helpers every command is written with: `query(cmd, preview, args)` for a command that answers with data, `act(cmd, args)` for one that just acts, `subscribe(event, handler)` for events. Outside Tauri (`npm run dev` opened in the browser) they answer with the preview and the page shows the "preview" banner: this way the pages render in the browser. They stay inside `ipc\`: pages do not call commands by name.
- A computed preview (`sampleStats()`) is written as `browserPreview ? … : invoke(…)`, so that it is not computed when the app is running.
- The types mirror the Rust structs with `serde(rename_all = "camelCase")`.

### Hooks (`shared\hooks.ts`)

- `useSubscription(onRun, handler)` registers a listener only once, passes every event to the latest `handler` and removes it on unmount even if the registration finishes later.
- `useEvery(read, ms)` reads right away and then every `ms`; `read` must be kept stable with `useCallback`.
- `useLoad(load, initial, { onError, every, enabled, key })` gives `{ data, error, reload, setData }`: it reads on mount, when `load` (stable with `useCallback`) or `key` changes, every `every` ms, and on every `reload`. With `enabled: false` it does not read. `onError` says what a failed read does: `"keep"` leaves the value as it was, `"show"` leaves it and puts the text in `error` (cleared by the next successful read), `{ fallback }` sets the fallback value. After unmount it writes nothing.
- `useAction(onDone)` runs an action with the wait state and the last error.
- `useCopy(resetMs)` copies to the clipboard; `copied` goes back to false after `resetMs`, if given.

Reads still written by hand, because `useLoad` would change what the user sees: an error that stays even after a successful read (`App.tsx` for the information, `shell\eject.tsx`, `settings\page.tsx`, `databases\page.tsx`, where the same error also covers start and stop); chained reads or reads that fill a form (`components\page.tsx`, `projects\editorsettings.tsx`); reads with arguments or with their own requests and wait state (`frameworks\model.ts`, `github\repos.tsx`, `components\relations.tsx`, `databases\browser.tsx`, `agents\stats.tsx`, `components\setup.tsx`).

Rules for whoever adds a control:
- fields and selects send a `change` that does not bubble: React's `onChange` on a hand-written `<vscode-*>` tag never fires. Use the wrappers (`VscodeTextfield`…) or a `workbench\` primitive;

- a color always comes from a theme variable (`--vscode-*` or a `vsc-*` token), never written by hand; the exceptions are VSCodium's fixed values (the red of the Close button) and the logo colors;
- a measure (height, width, padding, radius, shadow) always comes from `theme-sizes.css`: a `--vscode-*` size of VSCodium's registry or a `--vsc-size-*` token with its utility (`h-vsc-*`, `w-vsc-*`, `size-vsc-*`), never a number written in a component (D-142).

### Theme

A single source: `docs\brand\themes.py` resolves VSCodium's Dark Modern and Light Modern (`docs\brand\vscodium-themes\`) with the Atollo accent and writes four outputs.

- `tauri\editor-theme\`: the editor's "Atollo Dark" and "Atollo Light" themes;
- `ui\src\theme\theme-vscode.css`: for each theme about 800 `--vscode-*` variables, as VS Code gives them to its webviews, with the Windows fonts. The values, from weakest to strongest: the tables in `docs\brand\vscode-defaults\` (from `@vscode-elements/webview-playground` 1.9.0, MIT license), `BUILTIN`, `DERIVED` (the colors VS Code computes from a key changed by the brand, checked against the tables), the whole editor theme. Names as in the webviews: only the first dot becomes `-`;
- `ui\src\theme\theme-colors.css`: the `--vsc-*` color tokens for Tailwind, each one a `var(--vscode-…)`;
- `ui\src\theme\theme-sizes.css`: the sizes of VSCodium's registry (`--vscode-spacing-size*`, `--vscode-cornerRadius-*`, font sizes and weights, the modern UI's shadows), the workbench's own measures (`--pane-header-size`…) and the app's `--vsc-size-*` measures with their Tailwind utilities, the same in every theme.

The theme files come from a newer VSCodium than the one the kit ships: `RENAMED` gives their keys the names 1.135 reads, so the activity bar's item colors are `modernActivityBar.*`, in the app and in the editor theme alike. The sizes come from `docs\brand\vscodium-1.135\workbench-ref.css`, the part of VSCodium 1.135's workbench CSS the app mirrors (D-142), with the MIT license of Code-OSS: `node scripts/vscodium-css/extract.mjs` writes it from the editor's archive pinned in `components.json` (downloaded and checked with its SHA-256, or a path to an archive or to an extracted `workbench.css`) and fails on a `--vscode-*` key the app reads that this VSCodium does not know.

This way the app and the editor have the same colors and measures, key by key. A color is changed in `themes.py` (in `BRAND`), a measure in `LAYOUT`, then `python docs/brand/themes.py`; when the catalog pins another editor, first `extract.mjs`. `test\ui\theme\theme.test.ts` checks that every variable read by the components is defined in both themes, that every size is declared once with its utility, that the sizes are those of `workbench-ref.css`, that no token of the classic UI's parts is left and that VSCodium knows every `--vscode-*` key Atollo reads.
